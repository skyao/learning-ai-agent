## 什么是 "AI Agent"？


AI Agent = 以 LLM 为核心决策模块、能够在多步循环中自主决策行动（调工具/读写环境/产出中间结果）、依据环境或结果反馈迭代、直至完成目标的软件系统。

这个定义里有四个必须同时具备的要素：

1.  **LLM 为核心决策模块**（区别于规则、纯 RL、传统符号规划器）
2.  **多步循环**（区别于单轮问答、单次工具调用）
3.  **对环境/工具采取行动**（区别于纯文本输出）
4.  **反馈驱动的迭代**（区别于无状态的批处理）

下面是本次调研的 5 个决策点。

## Agent 边界清单

| 形态                                     | 判定（是/否）                         | 理由                        |
| ---------------------------------------- | ------------------------------------- | --------------------------- |
| 单轮对话（ChatGPT 问答）                 | ✗ 否                                  | 无多步循环、无行动          |
| 单次工具调用（"帮我查天气"→ 调一次 API） | ✗ 否（作为**背景能力**）              | 无迭代循环                  |
| Function Calling 本身                    | ✗ 否，归入**模型层能力**              | 是 Agent 的地基，不是 Agent |
| 多步工具编排、RAG+迭代、代码沙箱循环     | ✓ 是（弱自主）                        | 有循环有行动                |
| 自主编码 / 电脑操作 / Deep Research 类   | ✓ 是（核心对象）                      | 端到端任务型                |
| Copilot 式行级代码补全                   | ✗ 否，但存在"Copilot→Agent"的演化过程 | 无自主目标完成              |
| 传统符号 Agent / BDI / 纯 RL Agent       | ✗ 否，不算"LLM Agent"，但有历史渊源   | 无 LLM 决策                 |
| 多智能体协作（Multi-agent）              | ✓ 是，作为**一种架构形态**            | 属于 LLM Agent              |
| 具身智能/机器人/自动驾驶                 | ✗ 否，是相邻领域                      | 物理世界分支，体系不同      |

> 个人想法：这样切割之后，"AI Agent 发展史"就有了清晰的叙事边界——它讲的是**软件形态的、LLM 驱动的自主执行系统**从无到有的过程；而更早的符号 Agent 史只作为"前传"存在，避免调研变成一部 AI 通史。

## 能力栈分层

```bash
┌─────────────────────────────────────────────┐
│  应用层  端到端任务型产品（编码/电脑操作/研究/通用）  │
├─────────────────────────────────────────────┤
│  框架/协议层  编排框架 · 运行时 · 通信协议        │
├─────────────────────────────────────────────┤
│  模型层  LLM 原生 agentic 能力                 │
└─────────────────────────────────────────────┘
        （基础设施层横切：沙箱/评测/可观测/安全）
```



### 模型层

模型原生能力怎么一步步变强，是 AI Agent 历史发展主线之一。

- 推理协议（CoT → 隐式推理/推理模型）

- 工具调用（prompt hack 让模型吐 JSON → 结构化 function calling → 原生工具协议）

- 上下文窗口（4k → 100k → 200k → 1M+）——**这是自主执行长度的物理前提，不可忽略**

- 多模态输入（能否"看"屏幕/代码库/网页）

- 长稳与自我纠错

### 框架/协议层

把模型能力"编排"成系统的软件层

- 通用编排框架：LangChain → LlamaIndex → AutoGen 系 → Agent SDK 系
- 代码优先运行时：Claude Code、OpenAI Codex CLI、Gemini CLI、OpenHands 等
- 协议与标准：**MCP**（模型↔工具，2024-11 诞生）、**A2A**（Agent↔Agent，2025-04）、以及更早的 Assistants API / 各家 plugin/connector 生态
- 记忆与状态管理（早期 MemGPT → 长期记忆标准化）

### 应用层

端到端完成任务的产品，本次调研的重点

- 编码 Agent（任务最扎实、落地证据最多的一条线）
- 浏览器/电脑操作 Agent（general computer use）
- Deep Research / 研究型 Agent（检索→综合→成稿）
- 通用个人助理/行业 Agent（银行、客服、医疗等）

### 基础设施层

横切，不进主线当配角，而是当"校验器"

- 执行沙箱（安全性、能否安全自主）
- **评测基准**——要单独立展开，因为"能力宣称"vs"可验证成绩"之间的张力是 Agent 史反复出现的主题
- 可观测性 / 安全与对齐

### 层间接口

历史故事往往发生在接口上

- 模型层↔框架层：工具 schema 标准化、结构化输出
- 框架层↔协议层：MCP 让"接工具"从每家私有实现走向统一
- 应用层↔模型层：Agent 专用模型（如为 coding/computer use 微调的模型）

## 考察维度

每遇到一个里程碑或一个产品，都用同一套维度打分/定位，避免"各说各话、无法比较"：

| 维度         | 说明                                                         | 典型度量                                                     |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **自主度**   | 人类介入频率、监督方式（每一步确认 / 关键点审批 / 完全放手） | 可借鉴自动驾驶 L0–L5 的思路，但 Agent 无统一分级，需自行标注 |
| **能力范围** | 任务类型与领域宽度（单一编码 → 通用电脑操作）                | 基准覆盖、产品定位                                           |
| **可靠性**   | 成功率、可复现性、失败模式                                   | SWE-bench 类分数、真实用户留存                               |
| **经济性**   | 单任务成本、token 消耗、延迟                                 | 实测成本、厂商定价                                           |
| **扩展性**   | 能否处理长任务、跨会话记忆、规模化                           | 上下文、记忆机制、沙箱时长                                   |
| **影响力**   | 对后续生态的实际影响（不是自封的"革命"）                     | 采用量、衍生项目、被并入标准                                 |

**另外引入一个"机制维度"**：Andrew Ng 提出的 agentic 四模式——**Reflection / Tool use / Planning / Multi-agent collaboration** 可以作为"一个 Agent 内部在用什么机制"的标签，用来观察机制何时出现、何时变成标配。

## 判定标准

问题：什么事件有资格进入调研的故事主线？

个人想法：历史叙事必须防两种病：**流水账**（什么都记）和**成王败寇**（只讲赢家）。调用中按照这个逻辑来：先定"里程碑类型"，再定"采信门槛"。

### 里程碑类型

用途：判定一个事件时先进行归类。

六种里程碑类型：

1.  **首证型**：第一次证明某类能力可行（如 ReAct 证明"边想边做"）
2.  **工程化/产品化型**：把已证能力做成可用产品/API（如 Function Calling 把工具调用标准化）
3.  **标准建立型**：被多方接受成为事实标准（如 MCP 被多家采纳）
4.  **引爆型**：导致采用/资本/舆论的陡增（AutoGPT 现象、Cursor 爆发）
5.  **证伪/警示型**：证明某条路线走不通、或暴露重大局限（泡沫破裂、某范式被弃）
6.  **范式更替型**：改变整个领域的前提假设（如从"prompt 工程"到"训练 agent 专用模型"）

### 采信门槛

用途：写进调研结果前自问，避免捕风捉影。

- 有**一手来源**（论文/官方公告/代码仓库）吗？
- 当时真实影响 vs 事后追认的影响是否分清？（**这一点很重要**：MCP 发布时很多人没当回事，是后来才被追认为转折点——叙事要区分"当时热度"和"后世重要性"）
- 是否有**当时就存在的反方意见**（媒体报道的泼冷水、后续失败）？有就并列呈现。

## 检查机制

每次形成"这是一条发现主线"的判断前，过一遍反向检查：

1.  **幸存者偏差**：我们记住的都是活下来的（LangChain 主导过 2023，后来被大量批评——它算成功还是失败？）；死掉的大批 AutoGPT 衍生项目几乎无人记得，但它们定义了 2023 的舆论。
2.  **厂商叙事 vs 独立证据**：很多"里程碑"来自厂商公告（自封里程碑）。区分"厂商宣称"与"第三方验证"。
3.  **舆论温度 ≠ 实际能力**：AutoGPT 的 star 数远高于当时任何可靠 Agent——热度和能力要分开记录（调研中需要同时记两种信号）。
4.  **事后归因偏差**：把后来的结果强加为"当时就该看出"的必然。

## 术语表 

统一口径，防歧义

- **Agent / Agentic system / Agentic AI**：按工作定义，多数语境下可互换；"Agentic"强调"具有自主行动倾向"的属性形容词。
- **Agent loop / ReAct 循环**：思考→行动→观察→再思考的基本循环结构。
- **Tool calling / Function calling**：模型调用外部工具的接口能力；前者泛指，后者特指 OpenAI 2023-06 起标准化出的 API 形态。
- **Framework / Runtime / Protocol**：框架（开发库）、运行时（可直接使用的执行环境，如 Claude Code）、协议（跨系统标准，如 MCP/A2A）——三者常被混用，调研中要严格区分。
- **Autonomy level**：自主程度，无行业统一标准，调研中按具体任务的人机分工来标注。
- **Sandbox / Execution environment**：模型代码/行动的安全执行容器（Code Interpreter、容器、虚拟机）。
- **Eval / Benchmark**：评测基准——能力主张的可验证性来源（SWE-bench 家族、OSWorld、GAIA、WebArena 等）。
- **Memory**：短期记忆（上下文窗口）vs 长期记忆（跨会话持久记忆）。
- **Multi-agent**：多个 LLM 角色协作完成任务的架构形态。
- **Copilot（辅助）→ Agent（自主）**：调用中用来标注产品的自主度位置。
