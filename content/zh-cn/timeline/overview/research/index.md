## 什么是 "AI Agent"？

AI Agent = 以 LLM 为决策核心、能够在多步循环中自主决策行动（调工具/读写环境/产出中间结果）、依据环境或结果反馈迭代、直至完成目标的软件系统。

这个定义里有四个必须同时具备的要素：

1.  **LLM 为决策核心**（区别于规则、纯 RL、传统符号规划器）
2.  **多步循环**（区别于单轮问答、单次工具调用）
3.  **对环境/工具采取行动**（区别于纯文本输出）
4.  **反馈驱动的迭代**（区别于无状态的批处理）

下面是本次调研的 5 个决策点。

## 1. Agent 边界清单

| 形态                                     | 判定（是/否）                         | 理由                        |
| ---------------------------------------- | ------------------------------------- | --------------------------- |
| 单轮对话（ChatGPT 问答）                 | ✗ 否                                  | 无多步循环、无行动          |
| 单次工具调用（"帮我查天气"→ 调一次 API） | ✗ 否（作为**背景能力**）              | 无迭代循环                  |
| Function Calling 本身                    | ✗ 否，归入**协议**                    | 模型怎么接工具，是地基，不是 Agent |
| 多步工具编排、RAG+迭代、代码沙箱循环     | ✓ 是（弱自主）                        | 有循环有行动                |
| 自主编码 / 电脑操作 / Deep Research 类   | ✓ 是（核心对象）                      | 端到端任务型                |
| Copilot 式行级代码补全                   | ✗ 否，但存在"Copilot→Agent"的演化过程 | 无自主目标完成              |
| 传统符号 Agent / BDI / 纯 RL Agent       | ✗ 否，不算"LLM Agent"，但有历史渊源   | 无 LLM 决策                 |
| 多智能体协作（Multi-agent）              | ✓ 是，作为**一种架构形态**            | 属于 LLM Agent              |
| 具身智能/机器人/自动驾驶                 | ✗ 否，是相邻领域                      | 物理世界分支，体系不同      |

> 个人想法：这样切割之后，"AI Agent 发展史"就有了清晰的叙事边界——它讲的是**软件形态的、LLM 驱动的自主执行系统**从无到有的过程；而更早的符号 Agent 史只作为"前传"存在，避免调研变成一部 AI 通史。

## 2. 能力分层

年份页用四层切片看「该年 Agent 能踩在什么上」。这和单条里程碑的**分类**不是同一轴：分类回答「这条材料是什么」（论文还是产品）；能力栈回答「这一年四层各发生了什么」。

Function Calling 作为**能力**出现在模型层叙事里（决策核心开始能稳定调工具）；作为**里程碑**归入协议（它规定怎么接线）。Claude Code 作为能力栈里的运行时，分类是产品，不是框架。

```bash
┌─────────────────────────────────────────────┐
│  应用层  端到端任务型产品（编码/电脑操作/研究/通用）  │
├─────────────────────────────────────────────┤
│  框架/协议层  编排框架 · 运行时 · 通信协议        │
├─────────────────────────────────────────────┤
│  模型层  LLM 原生 agentic 能力                 │
└─────────────────────────────────────────────┘
        （基础设施层横切：沙箱/评测/可观测/安全）
```

### 模型层

模型原生能力怎么一步步变强，是 AI Agent 历史发展主线之一。

- 推理协议（CoT → 隐式推理/推理模型）

- 工具调用（prompt 里赌 JSON → 结构化 Function Calling → MCP / Skills 等可插拔协议）

- 上下文窗口（4k → 100k → 200k → 1M+）——**这是自主执行长度的物理前提，不可忽略**

- 多模态输入（能否"看"屏幕/代码库/网页）

- 长稳与自我纠错

### 框架/协议层

把模型能力"编排"成系统的软件层

- 通用编排框架：LangChain → AutoGen 系 → Agents SDK 系（分类：**框架**）
- 代码优先运行时：Claude Code、OpenAI Codex CLI、Gemini CLI、OpenHands 等（分类：**产品**，不是框架）
- 协议：Function Calling（模型↔工具的 API 方言）→ **MCP**（模型↔工具/数据，2024-11）→ **A2A**（Agent↔Agent，2025-04）→ **Skills**（运行时加载专长包，2025-10）
- 记忆与状态管理（早期 MemGPT → 长期记忆、频道记忆）

### 应用层

端到端完成任务的产品，本次调研的重点

- 编码 Agent（任务最扎实、落地证据最多的一条线）
- 浏览器/电脑操作 Agent（general computer use）
- Deep Research / 研究型 Agent（检索→综合→成稿）
- 通用个人助理/行业 Agent（银行、客服、医疗等）

### 基础设施层

横切，不进主线当配角，而是当"校验器"

- 执行沙箱（安全性、能否安全自主）
- **评测基准**——单独成**分类**，因为「能力宣称」vs「可验证成绩」是 Agent 史反复出现的主题（HumanEval → SWE-bench 家族 → OSWorld → Terminal-Bench）
- 可观测性 / 安全与对齐

### 层间接口

历史故事往往发生在接口上

- 模型层↔框架层：工具 schema 标准化、结构化输出（Function Calling 落在这条接口上，分类记协议）
- 框架层↔协议层：MCP 让「接工具」从每家私有实现走向统一；Skills 让专长可加载
- 应用层↔模型层：Agent 专用模型（如为 coding / computer use 微调的模型）

## 3. 考察维度

每遇到一个里程碑或一个产品，都用同一套维度打分/定位，避免"各说各话、无法比较"：

| 维度         | 说明                                                         | 典型度量                                                     |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **自主度**   | 人类介入频率、监督方式（每一步确认 / 关键点审批 / 完全放手） | 可借鉴自动驾驶 L0–L5 的思路，但 Agent 无统一分级，需自行标注 |
| **能力范围** | 任务类型与领域宽度（单一编码 → 通用电脑操作）                | 基准覆盖、产品定位                                           |
| **可靠性**   | 成功率、可复现性、失败模式                                   | SWE-bench 类分数、真实用户留存                               |
| **经济性**   | 单任务成本、token 消耗、延迟                                 | 实测成本、厂商定价                                           |
| **扩展性**   | 能否处理长任务、跨会话记忆、规模化                           | 上下文、记忆机制、沙箱时长                                   |
| **影响力**   | 对后续生态的实际影响（不是自封的"革命"）                     | 采用量、衍生项目、被并入标准                                 |

**另外引入一个"机制维度"**：Andrew Ng 提出的 agentic 四模式——**Reflection / Tool use / Planning / Multi-agent collaboration** 可以用来观察一个 Agent 内部在用什么机制、何时变成标配。这和里程碑的**标签**（首证 / 引爆等）不是一回事。

## 4. 判定标准

问题：什么事件有资格进入调研的故事主线？

个人想法：历史叙事必须防两种病：**流水账**（什么都记）和**成王败寇**（只讲赢家）。先定**分类**和**标签**，再定采信门槛。

时间线里每条里程碑：**分类只选一个**，**标签可多个**。侧栏 `linkTitle` 写成 `[分类]条目名`，例如 `[模型]GPT-4`。前传八条经典概念不套这七类。

### 分类（材料形态）

打开的是什么东西。七类：

1. **论文** — 剩余类。只有没有其他身份可挂时才进论文（ReAct、InstructGPT、PaLM、Aries）。
2. **模型** — 名字就是那只知名 LLM 的换核（GPT-3、GPT-4、Claude 3、o1、o3）。
3. **产品** — 可打开使用的应用或运行时（ChatGPT、Claude Code、Devin、Assistants API）。
4. **框架** — 编排库 / SDK（LangChain、AutoGen、Agents SDK）。
5. **协议** — 模型扩展能力的接线方式：Function Calling（模型↔工具）、MCP（模型↔工具/数据）、A2A（Agent↔Agent）、Skills（运行时↔专长包）。
6. **评测** — 考卷与基准（HumanEval、SWE-bench 家族、OSWorld、Terminal-Bench）。
7. **博文** — 工程实践指南（Building effective agents、Agent identity）。

归类规则：

- 有正式论文/技术报告，不等于分类是论文。知名模型走**模型**；评测论文走**评测**；可跑的系统走**产品**或**框架**。
- Function Calling 与 Skills 进**协议**，与 MCP、A2A 并列，都是扩展能力的不同切口；不是「又一只模型」。
- 厂商发布会不当一条。拆成当天真正改写 Agent 的对象（2023-11 记 GPT-4 Turbo、Assistants API，不记 DevDay；GPTs 不升格）。
- 同一对象跟主对象走：2025 云端 Codex 是产品，不是 2021 那只模型；Tag 的机制文档和 Slack 切换并进 Claude Tag。

对照例子：

| 条目 | 分类 | 标签 |
| --- | --- | --- |
| ReAct | 论文 | 首证 |
| GPT-4 | 模型 | 工程化 |
| ChatGPT | 产品 | 引爆 |
| Function Calling | 协议 | 工程化 |
| SWE-bench | 评测 | 首证、警示 |
| MCP | 协议 | 标准 |
| LangChain（2023） | 框架 | 工程化、警示 |
| Building effective agents | 博文 | 工程化 |

### 里程碑类型

作时间线的**标签**，可多个。六种历史角色，回答「为什么记进时间线」。表上用短名：

1.  **首证**（首证型）：第一次证明某类能力可行（如 ReAct 证明「边想边做」）
2.  **工程化**（工程化/产品化型）：把已证能力做成可用产品、API、运行时（如 Function Calling、Assistants API）
3.  **标准**（标准建立型）：被多方接受成为事实标准或默认考卷（如 MCP 被追认、SWE-bench Verified）
4.  **引爆**（引爆型）：采用、资本或舆论陡增（AutoGPT、Cursor、OpenClaw）
5.  **警示**（证伪/警示型）：某条路线走不通，或分数/安全把宣传拉开（SWE-bench 原版个位数、SWE-bench Pro 打回约 23%）
6.  **范式更替**（范式更替型）：改写领域前提（如从提示词循环变成推理模型、从个人终端变成组织身份）

分类和标签不要合成一套：GPT-4 不会因为「工程化」就改成产品；ChatGPT 不会因为「引爆」就不再是产品。

### 采信门槛

用途：写进调研结果前自问，避免捕风捉影。

- 有**一手来源**（论文/官方公告/代码仓库）吗？
- 当时真实影响 vs 后来才被看重的影响是否分清？（**这一点很重要**：MCP 发布时很多人没当回事，后来才被当成转折点——叙事要区分"当时热度"和"后世重要性"）
- 是否有**当时就存在的反方意见**（媒体报道的泼冷水、后续失败）？有就并列呈现。

## 5. 检查机制

每次形成"这是一条发现主线"的判断前，过一遍反向检查：

1.  **幸存者偏差**：我们记住的都是活下来的（LangChain 主导过 2023，后来被大量批评——它算成功还是失败？）；死掉的大批 AutoGPT 衍生项目几乎无人记得，但它们定义了 2023 的舆论。
2.  **厂商叙事 vs 独立证据**：很多"里程碑"来自厂商公告（自封里程碑）。区分"厂商宣称"与"第三方验证"。
3.  **舆论温度 ≠ 实际能力**：AutoGPT 的 star 数远高于当时任何可靠 Agent——热度和能力要分开记录（调研中需要同时记两种信号）。
4.  **把后来才清楚的重要性写成当时就已经注定。**

## 附录1：术语表 

统一口径，防歧义

- **分类 / 标签**：分类是材料形态（七选一）；标签是历史角色（六类，可多选）。侧栏 `[分类]条目名`。
- **Agent / Agentic system / Agentic AI**：按 AI Agent 定义，多数语境下可互换；"Agentic"强调"具有自主行动倾向"的属性形容词。
- **Agent loop / ReAct 循环**：思考→行动→观察→再思考的基本循环结构。
- **Tool calling / Function calling**：模型调用外部工具的接口；前者泛指，后者特指 OpenAI 2023-06 起的 API 形态。时间线上 Function Calling 的分类是**协议**，不是模型。
- **Framework / Runtime / Protocol**：框架（开发库，分类为框架）、运行时（打开就能委派的执行环境，如 Claude Code，分类为产品）、协议（扩展能力怎么接线，如 MCP / A2A / Skills / Function Calling）——三者常被混用，调研中要严格区分。
- **Autonomy level**：自主程度，无行业统一标准，调研中按具体任务的人机分工来标注。
- **Sandbox / Execution environment**：模型代码/行动的安全执行容器（Code Interpreter、容器、虚拟机）。
- **Eval / Benchmark**：评测基准，时间线上单独成分类（SWE-bench 家族、OSWorld、GAIA、Terminal-Bench 等）。
- **Memory**：短期记忆（上下文窗口）vs 长期记忆（跨会话持久记忆）。
- **Multi-agent**：多个 LLM 角色协作完成任务的架构形态。
- **Copilot（辅助）→ Agent（自主）**：用来标注产品的自主度位置。行级补全是产品，但按定义还不是 Agent。
