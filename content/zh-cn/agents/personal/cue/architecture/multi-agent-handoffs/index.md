## 官方给出的协作形态

资料描述多个代理在共同群聊中交接研究、筛选和内容制作，用户定方向并作最终决定。[团队场景](https://help.manus.im/zh-CN/articles/17190150-manus-2-0-有哪些新变化)

## 我的理解：交接需要包含可继续工作的状态

我用一个活动筹备任务来分析：研究代理给出场地，评审代理比较条件，写作代理生成材料。交接时只有推荐结果还不够，还要能查到来源、时间、容量限制、未确认条件和用户最新要求。

对自己的 Agent 平台，我会将下列内容作为交接检查项，而不是把一条群消息自动视为完整任务输入：

| 内容 | 我希望它解决的问题 |
| --- | --- |
| 目标与完成条件 | 接收方知道下一步要交付什么 |
| 关键事实与来源 | 能复核上游判断，发现资料变化 |
| 约束与未决问题 | 不把暂定结论改写成已确认事实 |
| 授权范围 | 接续工作不自动扩大对外操作权限 |
| 产物位置与版本 | 不误用旧清单、旧文件或其他任务结果 |
| 接收和验收记录 | 区分看到了消息、开始工作与完成交付 |

这是我的分析框架，不是已确认的 Cue 内部协议。

## 协作是否真的减少协调成本

我想观察三种状态是否可区分：代理表示愿意处理，代理实际开始，代理交付了可验收结果。如果每次都需要我重新分配、重复背景和提醒推进，代理数量增加未必能降低管理成本。

[英文第三方使用记录](../../practice/external-observations/)提供了交接需要人工跟进的一个小样本。我把它作为设计实验的线索，不能据此判断全部协作都会停在同一位置。

接下来我会分别看串行交接、并行研究后合并和中途改变目标，并记录误差怎样传到下游。具体输入与验收口径见 [实践计划](../../practice/validation-plan/)。
