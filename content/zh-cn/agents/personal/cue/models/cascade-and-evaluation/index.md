## 发布文章说了什么

Cascade 被介绍为自研 Agent Harness 的一次迭代，按工作需要引入专业能力。官方给出一项测试配置：token 减少 23.2%、完成时间缩短 28.2%、运行成本降低 32%，比较对象是此前系统。这不是全任务平均数，也不是 Cue 的独立可靠性评测。[原始声明](https://www.manus.im/blog/introducing-manus-2-0)

## 我怎样看待这组指标

对平台开发，这些指标分别涉及输入输出规模、等待与执行时间，以及底层费用。它们可能受到模型、缓存、工具调用、并发和重试等多项因素影响。仅有百分比，尚不能解释改进发生在哪一段链路。

我想核实的是测试任务、成功条件、模型与预算是否可比，减少的开销是否以同等交付质量为前提，以及错误恢复和人工介入是否计入成本。当前发布资料不足以独立复现这些结果。

## 模型层目前保留的信息缺口

在这轮已读的 Cue 发布、帮助与商店资料中，我没有拿到足以对应具体账号的模型版本、路由和推理预算，也没有找到可复核的 Cue 专项模型卡。这里不填猜测名称，更不能从 Manus 过去使用的模型推定当前 Cue 配置。

同样，Manus 2.0 或 Cascade 的更新不能直接等同于 Cue 每类任务的同比提升。基础设施共享提供了研究线索，还需要具体产品路径与实验条件。

## 我准备采用的产品评估口径

| 要回答的问题 | 我希望同时保留的证据 |
| --- | --- |
| 是否理解要求 | 原目标、变化的约束与任务输入 |
| 是否完成交付 | 文件、外部回执和验收结果 |
| 是否支持协作 | 交接次数、信息丢失和人工提醒 |
| 是否能长期推进 | 触发、阻塞、恢复与停止原因 |
| 成本是否下降 | 整项职责的用量、资源订阅与人工时间 |

我会把模型配置与运行条件一起记录，再比较产品效果。跨产品问题留到相应实验完成后判断，当前只整理 [待实测方案](../../practice/validation-plan/)。
