## 这一轮我完成了什么

第一批当前包含 **8 个对象**：Muse、Dots、Cue、Gemini Spark / Task、Grok Bot、OpenClaw、**WorkBuddy** 和 **Claude Duet**。前六个对象资料核验于 **2026-10-21**，WorkBuddy 保留 **2026-10-22** 资料，Duet 于 **2026-10-23** 补入。[Personal Computer](../personal-computer/) 调入[第二批](../second-batch-summary/)作为参考，[Claude Cowork](../claude-cowork/) 也保留在第二批。每个目录都按产品、架构、模型、工具、安全、实践组织，保留资料索引和最后的总结。

我想回答的主问题始终是：**Personal Agent 怎样从理解个人上下文，走到能够长期受托推进工作？** 这与我正在做的 Agent 运行平台和开发直接相关。八个样本帮助我将问题拆得更细，但还不足以判断谁在我的工作中效果最好。

本轮没有新增账号、设备或部署实测。Muse 原有个人探索继续作为单独证据，代理自述和独立观察分别保留。其他产品主要依据公开文档、发布资料和外部观察；下表是我的阅读脉络，不是市场分类或能力排名。

## 我从八个样本中分别学到了什么

| 样本与总结 | 我重点学习的路线 | 最值得带回平台开发的问题 |
| --- | --- | --- |
| [Muse](../muse/summary/) | 持续工作环境、长期目标和安全设计 | 任务如何跨运行实例延续，授权和副作用如何一起恢复 |
| [Dots](../dots/summary/) | 长期职责、任务委派与个人上下文 | 目标更新如何传到派生工作，结果如何带着证据回传 |
| [Cue](../cue/summary/) | 独立身份、通信资源与代理团队 | 请求者、执行者、凭证主体和交接责任怎样对应 |
| [Gemini Spark / Task](../gemini-spark/summary/) | 原生应用生态、计划与方法 | 数据更新、触发、不同执行路径和用户控制如何一致 |
| [Grok Bot](../grok-bot/summary/) | 长期角色与共享云端电脑 | 职责分开以后，共享文件、登录态与并发如何管理 |
| [OpenClaw](../openclaw/summary/) | 自建运行、设备路由与自动化 | 控制面、宿主、模型服务和运营者分别承担什么 |
| [WorkBuddy](../workbuddy/summary/) | 国内办公生态、个人记忆、项目与本地 / 云端任务 | 个人与项目上下文、远程入口和后台运行怎样对应 |
| [Claude Duet](../claude-duet/summary/) | 主动发现、持续跟进与用户决策交回 | 检查频率、打扰质量、共享记忆和任务验收如何一起评价 |

这些关注点不代表其他产品缺少相应设计。公开程度、版本和研究材料不同，只能在证据允许的范围内比较。

## Duet 补充了什么比较问题

这次补入 [Claude Duet](../claude-duet/)，我更关注主动性怎样转成可评价的系统行为：何时读取来源、哪些变化值得处理、什么时候需要用户决定，以及产物与任务验收怎样对应。检查存在采样间隔，所以通知时延还需要与判断错误分开分析。

我在第二批保留 [Cowork](../claude-cowork/) 的知识工作路线，不把 Duet 写成它的更名或替代。共享账号记忆和应用配置可以减少背景说明，但不代表所有项目、文件与任务都可相互读写。具体比较见 [Duet 与 Cowork](../claude-duet/product/positioning-and-cowork/)。

下一轮同一场景除了检查完成产物，还会记录有效发现、漏报、无效打扰、审批等待与后台预算。本段依据 2026-10-23 新读资料，其余样本仍保留各自原有核验日期。

## 个人上下文：从有记忆到能更新事实

各产品都让我回到同一个问题：长期保存信息以后，系统怎样知道什么仍然适用？我现在会分开记录原始来源、历史对话、可复用记忆、项目约束和当前上下文。

偏好可以长期沿用，会议时间和授权范围则应在执行前重新核实。一次任务中的临时要求，也未必应该覆盖长期设置。真正值得验证的是，纠错是否进入后续运行，旧信息为什么仍会被召回，以及不同项目的事实是否混在一起。

[OpenClaw 的来源与后台记忆整理](../openclaw/architecture/memory-and-dreaming/)、[WorkBuddy 的个人记忆与项目](../workbuddy/architecture/memory-and-projects/)与 [Claude 的项目记忆](../claude-cowork/architecture/projects-and-memory/)给了我不同的阅读切口。它们还不能直接用于比较“记忆最好”，下一步需要统一的事实更新实验。

## 运行环境：把规划、资源和动作的位置分开

“本地”与“云端”都太粗。一次任务可能在云端组织工作，读取桌面文件，再用某个已登录的浏览器提交结果。本地工具执行也不意味着模型推理、上下文和全部数据都留在本机。

我会分别记录以下对象：

| 对象 | 我希望平台能解释的问题 |
| --- | --- |
| 任务与会话 | 谁保存目标、进度和待决事项 |
| 计算环境 | 代码在哪执行，停止和恢复依据什么 |
| 设备与文件 | 设备离线后哪一步不可用，读取内容去了哪里 |
| 登录态与凭证 | 实际动作代表谁，授权怎样撤回 |
| 产物与外部结果 | 运行结束后还留下什么，是否可再次修改 |

[Grok Bot 的共享电脑](../grok-bot/architecture/shared-runtime/)尤其提醒我，多个角色不自动构成隔离。[OpenClaw 的信任边界](../openclaw/security/trust-boundary/)则区分个人可信运行与互不信任用户的托管。[Claude 的新旧运行路径](../claude-cowork/architecture/runtime-boundaries/)还说明，产品演进会改变同一个名称下的环境条件。

## 持续执行：目标、计划与单次运行分别管理

我现在更愿意用可检查的对象理解“持续工作”：目标是什么，何时触发，用什么方法，这一轮实际执行到哪一步。保存了计划，不代表宿主、连接器和模型服务在触发时都可用；云端仍在运行，也不代表能够继续访问断线设备。

暂停下一次触发、取消当前运行、撤销访问和删除记录，各自影响的对象不同。长期委托还需要在目标完成或条件改变时调整后续动作，不能只靠重复运行同一个提示。

相关资料分别见 [Spark 任务与计划](../gemini-spark/architecture/tasks-and-schedules/)、[OpenClaw Automations](../openclaw/architecture/automations/)、[WorkBuddy 排程与运行](../workbuddy/architecture/schedules-and-runs/)与 [Claude 定时任务](../claude-cowork/architecture/scheduled-tasks/)。文档之间仍有离线条件或迁移范围的差异，我保留问题，不补写未公开实现。

## 用户控制：沿着真实动作检查

工具接入改变了系统可以看到什么，也改变了它能对现实对象做什么。我会把方法复用和授予能力分别看：Skill 可以表达工作步骤，Plugin 可以组合配置，真正动作仍取决于工具、运行位置与授权。

浏览器、连接器、代码和屏幕操作可以到达相似结果，权限粒度与证据却不同。一个通道受到限制后，是否允许改用另一个通道，需要沿用户的实际批准范围判断。

[Cue 的身份与团队](../cue/)、[Grok Bot 的 Team Bots](../grok-bot/architecture/team-bots/)、[Muse 安全设计](../muse/security/)和 [Claude 权限](../claude-cowork/security/permissions-and-network/)分别提供了身份、资源、审批与动作检查的线索。对我做平台，最终要能够解释谁请求、谁批准、代表谁执行，以及撤权以后还发生了什么。

## 可观测性与成本：解释一次任务为何成功或失败

只看最终回答，很难区分资料过期、模型误判、工具失败、设备断线和用户拒绝。我的任务记录需要关联来源、模型、工具、审批、环境和产物；恢复以后，还要确认外部动作是否已完成，避免重复副作用。

[Claude 的 OTel 资料](../claude-cowork/security/observability/)提供了具体的事件参考，[OpenClaw 的运维笔记](../openclaw/practice/operations/)则让我把备份、升级和业务恢复加入评价。事件可采集与业务可复盘仍需分别验证。

成本也需要按完整工作计算：订阅或模型用量、宿主与硬件、等待时间、人工审批、修订和维护。不同账号的功能范围与额度不一致，不能只把价格或一次调用费用放在一起比较。

## 下一阶段如何用实践收敛判断

我准备先使用同一份合成材料包，以学习资料维护为主线，按以下顺序验证。下面是实验设计，尚无统一实测结果。

| 场景 | 我想核实的行为 | 保存的证据 |
| --- | --- | --- |
| 调研并生成可编辑文件 | 来源、事实、格式与最终交付 | 原始资料、引用、产物及人工修订 |
| 主动检查与关注度判断 | 采样时延、漏报、打扰与审批 | 来源变化时间、检查与通知、用户决定、用量 |
| 更新一个关键事实 | 新旧约束与跨项目上下文 | 修改前后任务、记忆和实际输出 |
| 执行中断与恢复 | 等待、重试、重复副作用 | 中断点、状态、回执及恢复结果 |
| 周期任务遇到资源不可用 | 跳过、暂停、恢复与通知 | 计划定义、各次运行和失败原因 |
| 运行期间撤销访问 | 派生工作是否同步收敛 | 撤权时间、工具结果和审计记录 |
| 多代理分工处理同一资料 | 交接、一致性和协调成本 | 输入版本、分工、冲突与最终结果 |

每次实验先记录套餐、地区、客户端与服务版本、工具配置、权限和完成标准。条件不相同的能力先说明范围；尚不可用的功能不推定为永久缺失。

这一轮形成的认识会继续随着实践修正。原始来源仍保留在各产品的资料索引中，[调研清单](../research-list/)记录范围和进度，这篇笔记用于把阅读之间的联系保存下来。
