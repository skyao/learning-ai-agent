## 原文要点

官方发布 Muse Spark Open 的模型权重，介绍多模态理解及长流程 Agent 工作，并展示在特定桌面硬件上通过 Muse Code 运行的案例。权重采用 Muse Model License，包含商业条款。具体硬件、推理框架和许可条件应到原文及模型卡核对。

## 我的理解：分别看模型、执行系统和服务

读这次公告时，我按自己做平台的职责边界拆成三层：

- 模型层：权重、推理框架、运行资源和许可证。
- 执行系统：Harness、工具、任务调度、记忆和权限管理。
- 产品服务：账号、云端环境、支付与对外通信。

本次开放为模型层提供了新的研究入口。完整个人代理仍需要执行系统和服务配合，不能由此推断 Muse 服务整体开源，也不能把 Muse Code 的本地案例视为 Muse App 的默认架构。

## 对后续自建比较的启发

如果尝试本地搭建，我会分别记录模型、Harness 和连接器的来源与版本，核对各自许可，再观察任务完成质量与资源开销。这样才能判断迁移成本究竟来自推理部署，还是来自工具、身份和持久状态等产品能力。

这里尚无本地部署结果。关联资料：[Gadget SDK](../../integrations/muse-gadgets/)开放的是设备接入能力，属于另一层的参考实现。

## 补充（2026-10-29）：许可细读给出的合规边界

来源：XT.PT 对 Muse Model License 的分析（2026-10-28 发布，作者称原始许可与模型卡阅读于 2026-10-27）。我没有逐条复核 Hugging Face 上的 LICENSE.md 原文，所以下面记为「引用许可条文的二手分析」，不是我本人的法律核查结论，也不构成法律意见。

- 署名义务跟着衍生品走：第 2 条要求在产品 UI、文档、网站或设置菜单中显著展示「Built with Muse Spark Open」；「衍生品」定义覆盖用其输出训练出的模型，即使不含 Meta 一个参数。按这个定义，训练管线要记录哪些数据集由 Spark Open 生成，因为血缘决定哪些模型带署名。
- 服务门槛按集团收入算：第 3 条针对 Model as a Service（以 API 或类似接口向第三方提供模型输出）。被许可方及其关联方在任何连续 12 个月内的合计总收入超过 2,000 万美元时，须在提供服务前通知 Meta 并签订单独书面协议；内部使用与研究不触发，许可中也没有用户数量门槛。
- 第 4 条：Meta 对用本软件生成的输出不主张所有权。

我的理解：这篇细读把「开放」从参数规模叙事收窄为可执行的合规边界。小团队与研究者层面是「用、署名、守使用政策」；想卖 API 且集团收入超线者要先谈协议。待核验：Hugging Face LICENSE.md 第 2、3、4 条引文逐条直读，以及该许可在 2026-10-15 之后有无修订。
