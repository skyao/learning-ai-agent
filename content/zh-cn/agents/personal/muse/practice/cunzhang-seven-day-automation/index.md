## 我为什么收录这一篇

这是我见到的首篇简体中文持续运行类实测。此前简体中文任务执行类的记录只有优哥跨境的单次会话五类任务（约 50 秒到 3 分钟的单次任务），而这一篇测的是另一维度的能力：无人值守连续运行一周。7 天里每日 3 档 10 秒短视频＋X／Threads／IG 共 7 次定时发布「一次没落下」，免费额度一周用 82%。我收录它，是因为它把证据从「单次任务成败」推进到了「固定节律任务的连续可靠性」，同时给出一份具体的平台摩擦清单——而这份清单恰好说明，链路里真正需要人手的地方不在 Muse 内部，而在平台一侧。

## 实测设置（先记条件，再看结论）

任务固定为每天 8:30、11:30、18:30 各做一条 10 秒科技短视频，打包上传到作者自写的开源中转服务 CunFetch（部署于 Cloudflare 免费存储，Muse 持 API Token 上传视频、封面与标题 JSON）；X、Threads、IG 三个账号每日发帖；另有博客动态维护与 SEO／GEO 检查等杂活。链路是：Muse 云端电脑产出 → CunFetch 中转 → 作者本地 Windows 定时任务在发布前拉取 → 自写 CunPush 一站式分发；视频号目前为手动发布。

作者的一条经验我单独记下：任务描述越具体执行越稳，起初任务太笼统、返工好几次后才收敛到固定时刻与固定产出格式。这与我此前记下的「给目标、不给步骤」官方口径形成对照——官方口径成立的前提是任务本身已被收敛成固定节律，开放式任务仍需人工收敛。

## 7 天结果（作者自述）

- 成功：连续 7 天，每日 3 档视频素材与 7 次定时发布全部完成，「到点就干活」；博客动态、SEO 检查等杂活亦顺手完成；免费额度内 0 元，一周用 82%，平台赠送的 310 亿词元（作者表述的赠送量，来源构成未说明，我不把它对应到官方邀请码规则）一分没动。
- X 与 Threads 由 Muse 用自有浏览器登录后发布；IG 走官方 API。
- 火柴人视频 skill（kaomei 开源的 stickman-video-director，作者「喂」给 Muse 按导演提案加分镜流程出片）作者称「目前还在测方向」，我不计入 7 天成功清单。

## 摩擦清单（作者自述，平台侧原因未获平台方证实）

| 摩擦点 | 现象 | 我的区分 |
| --- | --- | --- |
| Threads 确认卡 | 每次发布须点一次确认卡，作者称绕不过去 | 这是审批机制本身，不是故障；我把确认卡记为持续自动化链路中无法消除的人工节点 |
| 小红书 | Muse 的机房动态 IP 段被封禁，直接登录不上 | IP 段风控，与 Amazon 封堵、银行封凭证登录同属「平台选边」线，但性质不同：此处是 IP 段风控而非 agent 身份政策 |
| 视频号 | 直接自动发布十次里总有几次失败，改中转＋本地手动发布才稳定；登录态仅维持一两天、须重扫 | 我把登录态有效期记为链路外的运维成本 |
| 账号安全 | 作者提示只给 API 权限、勿给 admin 账号密码；X 一旦出现验证或限流提示立刻停手 | 作者观点，我转述为操作建议，不作官方安全口径 |

## 我从这一篇提炼的实践区分

- 自动化解决的是「动手」问题，不解决「动脑」问题——这是作者的原话，我认同并记下：账号能否做起来看运营思路，而非自动化本身。这一篇的 7 天零缺席证明的是执行节律的可靠性，不是内容质量的保证。
- 与 Pat Simmons 三方对照的张力我必须同时记下：同一产品，在固定节律的内容生产任务中 7 天零缺席，在开放式多系统经营任务中却出现「谎称已处理、实际未做」。两者任务类型不同（固定节律 vs 开放式多系统），不得互相否定；我从中得到的区分是：固定节律＋中转缓冲的任务形态在本篇中跑通了 7 天，而开放式经营任务的汇报可信度仍是未解问题。
- 用量对照：本篇 7 天定时短视频＋发帖用掉免费额度 82%，MaliLion 两日集中生成约 30 支视频用掉 2%→85%——不同任务类型的消耗曲线不同，我不把两者合并成统一用量曲线。

## 待验证

- 7 天零缺席为单作者单链路样本，CunFetch／CunPush 为作者自写工具链，链路含本地定时任务与手动发布环节，不得读作 Muse 端到端独立闭环。
- 小红书 IP 段封禁与视频号登录态有效期均为作者单方观察，未获平台方证实；若有第二家中文实测报告同类摩擦，我再比较。
