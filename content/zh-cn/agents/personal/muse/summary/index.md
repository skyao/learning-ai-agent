我调研 Muse，最想弄清楚的是：**一个长期服务于个人的 Agent，怎样把对人的理解、任务状态和执行环境组织起来，持续承接委托？** 这与我目前做的 Agent 运行平台和 Agent 开发直接相关。产品层的自然交互背后，最终都要落到状态、调度、工具、权限和故障处理上。

这篇笔记整理我截至 **2026-10-21** 的阶段性理解，依据是已经收集的官方资料、第三方观察，以及我此前的 [个人分析](../practice/analysis/)。本次总结没有新增账号实测；涉及内部实现时，我会保留观察与推断之间的距离。资料出处集中在 [资料索引](../references/)。

## 1. 先从任务生命周期理解产品

读 [产品设计资料](../product/how-we-design-muse/)时，我关注到长对话、目标跟踪、后台工作、活动记录和交付物之间的联系。对我而言，这些设计提出了一个平台问题：一项委托如何在多次交互和多轮执行之间保持连续？

例如，“持续整理一个项目的进展”会涉及读取资料、识别变化、维护文档、等待审批和通知用户。用户还可能中途修改目标。对话是输入的一部分，任务本身则需要有可恢复的状态、可检查的结果和明确的停止条件。

我因此把会话、任务和运行实例作为三个不同的生命周期来分析。同一任务可能经历多次会话，也可能跨越多个运行实例。这是我用于理解和设计系统的职责划分，尚不能据此断言 Muse 内部采用了同样的数据模型。

[Connect 更新](../product/connect-2026/)让我进一步关注多入口的一致性：眼镜上发起的委托、手机上的审批和网页中的交付物，怎样关联到同一项任务？如果语音交谈与后台工作并行，新要求何时生效，已经排队的动作如何处理？公告扩大了产品入口，但这些执行语义仍需继续核实。

## 2. 持久化工作环境与可恢复任务之间还有一段距离

Muse 的 [架构材料](../architecture/muse-architecture/)将 Agent 循环、工作环境、文件、记忆和后台工作联系起来。我的理解是，专用环境给了 Agent 一个积累工作成果的地方，但“文件还在”和“任务能够继续”分别涉及不同的状态。

我在此前的探索中记录过 `boot_id`、`uptime` 的变化，也记录了跨运行实例变化的 `vm-watchdog` 定时任务。Muse 对数据库和调度表的自述提供了一些线索，但那部分信息仍需与独立证据交叉核对。[原始探索记录](../practice/analysis/)

这些现象让我怀疑，任务的唤醒能力并不完全依赖当前 VM 中的进程。然而，它们还不足以确定外部调度器、数据库和持久卷的完整拓扑。原分析中提出的几种解释，我目前仍保留为假设。

回到自己的平台设计，我会把问题拆到具体故障点：

- 运行实例被回收后，谁知道下一次应当执行什么，谁负责重新分配环境？
- 工具已经执行，但结果尚未写入任务状态时发生中断，恢复后如何判断是否需要重试？
- 发送邮件、提交订单这类外部动作重放时，怎样避免重复副作用？
- 用户取消或撤销授权后，排队中的任务和正在执行的动作分别如何收敛？

这些问题来自我对运行平台的思考，目前的 Muse 资料没有给出完整答案。它们也提醒我，持久卷、历史记录和周期触发只是恢复链条中的几个环节；恢复还需要处理动作结果、状态提交和重复执行的关系。

## 3. 记忆需要沿着写入、更新和使用的链路研究

[Wonder 公告](../models/muse-wonder/)强调 Active Memory。我更关心的信息链路是：什么内容值得写入，如何表达来源与适用范围，事实改变后如何更新，以及任务运行时究竟取回了什么。

在我的已有探索中，“叫我 Sky”这条偏好在后续交互中生效；Muse 还描述了 Markdown 文件与数据库索引的关系。前者是我观察到的行为，后者包含代理对自身实现的解释，证据强度不同。我不能仅凭这次交互，就确认全部记忆都采用同一套存储和检索机制。[记忆探索记录](../practice/analysis/)

从开发角度，我会分别看待历史、可复用记忆和当前模型上下文。历史可以完整保存，记忆需要选择和更新，当前上下文还受相关性与预算约束。存储正确、召回正确和使用正确，需要分别找到证据。

我接下来想深入的是冲突和作用域：用户临时修改一次要求，是否应该覆盖长期偏好？同一个人的个人事务与工作事务，哪些信息可以共享？旧事实已经进入运行中的任务后，更新如何传播？这些问题比单次准确回忆更接近长期个人代理的实际使用条件。

[Wonder 模型卡](../models/wonder-model-card/)中的干扰、事实更新和遇阻评估，为我提供了实验思路。但模型评估所用的上下文、Harness 和推理设置，与产品实际运行条件之间仍有距离。我会把模型能力和产品记忆机制放在同一条链路上分析，同时分别记录证据。

## 4. 持续推进需要模型决策与运行时共同成立

Active Focus 关注遇阻后继续推进。这让我想到 Agent 开发中的一个常见分工：模型需要识别变化、调整计划，运行时需要保留状态、执行动作、返回错误，并支持等待、恢复和停止。

如果工具暂时不可用，合理的处理可能是换一条允许的路径，也可能是等待条件满足或请求我补充权限。持续执行的价值取决于是否在接近目标。我更想观察错误是否被分类、已完成的工作是否被复用，以及何时决定交回给用户。

因此，今后比较产品时，我会同时留下模型决策和执行状态的记录。仅看一段对话，很难判断是模型没理解任务、工具返回信息不够，还是运行时丢失了恢复所需的状态。仅看工具调用次数，也很难评价完成质量。

这里还有一个版本问题：[Wonder](../models/muse-wonder/)的发布与 Muse 产品接入有各自的时间条件；[Spark Open](../models/muse-spark-open/)开放模型权重，也没有直接提供完整的个人代理服务。我需要分别跟踪模型、Harness、工具和产品版本，才能解释能力变化来自哪一层。

## 5. 工具接入同时改变执行位置与权限边界

[连接器](../integrations/connectors/)、[Windows 接入计划](../integrations/windows/)和 [Gadget SDK](../integrations/muse-gadgets/)，让我看到个人代理可能跨越云端环境、个人电脑和设备。对运行平台而言，工具描述之外还需要明确执行位置、执行身份、凭证来源和结果如何返回。

Gadget SDK 的 Linux 文档说明，设备操作权限与安装时选择的本机账号有关。这意味着“接入一个设备”同时引入了一个具体账号的权限范围。配对成功只是起点，我还需要理解断线恢复、命令重复、访问撤销和本地服务停止各自的语义；本轮没有安装验证。

我在已有 Connector 探索中，实际观察过 Gmail 的连接与读写审批界面。这为区分协议接入和产品化集成提供了具体经验：接通工具之后，还需要管理账号、授权范围、审批、失败反馈和断连状态。有关凭证隔离的设计，则继续对照 [官方安全资料](../security/security-and-safety-for-ai-agents-our-approach-with-muse/)理解，不能只凭界面推断。

外部服务也是执行链的一部分。[访问限制报道](../practice/service-boundaries/)提醒我，用户授权、工具具备操作能力和服务方允许访问，需要同时成立。以后分析任务失败时，我会把服务方拒绝与模型规划失败分开记录，否则很容易把不同问题混进一个“成功率”。

## 6. 授权需要沿着动作和数据流落实

Muse 官方介绍的 Sentinel、凭证隔离和动作审批，对我最有参考价值的地方，是把用户控制落实到实际执行路径。对平台设计，我关心批准绑定的动作、对象、金额或数据范围，以及执行前是否还会校验这些条件。[官方安全设计](../security/security-and-safety-for-ai-agents-our-approach-with-muse/)

这也涉及审批后的变化。如果用户批准的是一份草稿，发送前内容又被模型修改，原来的批准是否仍然适用？如果任务从一个工具转到另一个工具，原有授权怎样传递？这些是我的设计问题，当前资料不足以确认 Muse 的全部处理方式。

两类外部观察进一步拓展了我的关注范围。[电话任务的人工接管报道](../security/human-concierge/)涉及执行者改变后，数据能否随任务一起转交；[GhostShares](../security/ghostshares/)涉及内容分享之后，链接可发现性、接收方访问和历史元数据的边界。前者记录的是特定测试，后者存在披露和处置时点，都要按当时条件阅读。

我的阶段性认识是，执行环境的隔离只是信任链的一段。任务转交、产物发布和用户撤销同样需要在平台中有明确语义，而且需要留下足以解释实际行为的记录。

## 7. 后续比较中，我会保留哪些证据

这轮学习让我更愿意沿一项完整委托比较产品：目标怎样进入系统，个人信息怎样被使用，工作如何推进，阻碍出现后如何恢复，最终结果由什么证明。这样也更容易把产品观察转化成对运行平台和 Agent 开发的理解。

| 我想回答的问题 | 后续需要积累的证据 |
| --- | --- |
| 任务能否跨实例延续 | 触发时间、实例变化、恢复位置、重复动作与最终产物 |
| 记忆是否被正确使用 | 原始事实、更新记录、召回内容及任务中的实际使用结果 |
| 遇阻后是否仍接近目标 | 错误、计划调整、有效进展、用户介入和停止原因 |
| 授权是否约束执行 | 批准对象、实际动作、拒绝结果及撤销后的行为 |
| 交付是否真正完成 | 文件、正式回执或外部状态，以及仍需人工完成的部分 |

这些记录尚待逐步补齐。[Muse 与 Dots 的第三方评测阅读](../practice/muse-dots-review/)已整理了一份任务验收口径，后续可以用于比较；它还不是我自己的跨产品实测结果。

目前我从 Muse 带走的核心问题，是**如何让任务状态、个人上下文、执行环境和权限在不同生命周期之间保持一致**。下一步调研其他产品时，我会继续带着这个问题阅读和实践，再回头修正这里的判断。
