调研 Dots 时，我最关注的是：**个人代理如何把一个长期目标拆成不断变化的任务，并在委派、等待和恢复的过程中保持目标与授权一致？** 这比单次对话能否答好问题，更接近我目前做运行平台与 Agent 开发时面对的工作。

这篇笔记基于截至 **2026-10-21** 的公开资料。来源与时间见 [资料索引](../references/)，本轮没有账号实测。下面既有资料阅读后的理解，也有我对平台设计的延伸问题；不足以确认的内部实现继续留白。

## 1. 长期职责需要独立于一次任务来理解

[发布资料](../product/introducing-dots/)与 [任务文档笔记](../architecture/tasks-and-delegation/)让我把持续职责、具体任务和会话分开思考。一个任务可以结束，但“持续跟踪某个项目”仍可能派生下一项工作。

我目前的理解是，长期代理需要维护目标、当前判断、待办和决策点之间的关系。用户回来补充要求时，系统需要知道这句话是在修正哪项职责、影响哪些任务，而不只是把新消息接到历史末尾。

这也改变了我对产品效果的评价方式。我想看代理是否减少了我反复整理背景和催促跟进的工作，同时保留足够的控制与解释能力。

## 2. 委派让上下文选择成为显式问题

Dots 的公开资料给出了多种任务与环境的关系，我在 [运行边界分析](../architecture/runtime-boundaries/)中按职责整理了一遍。对自己的平台设计，我更关心委派时交出去的目标、约束、证据和批准范围是否足够清楚。

委派带来并行机会，也带来上下文分叉。主对话里的新决定要传到哪些任务，子任务返回的结论又依据哪个版本的事实，都需要可追踪。如果只保留一段汇总结果，很难解释为何某项工作仍按旧要求执行。

因此，我想在实践中沿着目标变化和结果回传观察系统，而不先把“并行 Agent 数量”作为主要指标。这里尚没有任务日志可证明 Dots 的一致性处理方式。

## 3. 记忆的价值要与更新和管理一起看

[记忆笔记](../architecture/context-and-memory/)让我更明确地区分来源共享、代理自己的长期笔记和当前任务输入。这些表示之间的联系，比“记住了多少信息”更值得研究。

例如，一条临时要求只适用于当前任务，长期偏好则可能影响未来多个任务。如果系统无法表达适用范围，就可能让一次性的变化长期生效，或让旧事实进入新的工作。

对我而言，下一步更有价值的证据是：更正之后哪些任务使用了新事实，以及旧信息为什么仍在某些地方出现。信息来源和输入版本能够帮助定位这类问题，当前资料还不足以确认完整实现。

[数据生命周期笔记](../security/data-lifecycle/)则补充了另一个方向：继续取数的权限、已有记忆和已生成的产物，需要分别管理。长期代理的“了解我”也意味着要解释信息怎样更新与离开系统。

## 4. 混合执行需要保留环境归属

[电脑与会话笔记](../integrations/computers-and-sessions/)使我更关注任务、设备、文件和登录状态之间的归属关系。云端协调与本地执行组合之后，用户看到的是一项工作，平台面对的却是多个可用性和权限边界。

设备离线时如何等待，环境改变后能否继续，外部动作已成功但回执丢失时怎样重试，都是我想进一步验证的运行问题。仅有文件持久化，仍不足以回答这些问题。

我还需要区分“执行位置”与“数据处理位置”。本机工具执行成功，并不能由此确认全部任务上下文只在本地处理。企业策略也应沿实际执行路径核对，详见 [治理笔记](../security/enterprise-governance/)。

## 5. 用户控制需要覆盖派生工作

[安全设计](../security/safety-design/)和 [控制语义](../security/controls-and-cancellation/)对我的主要启发，是把权限检查、执行隔离、动作审查和停止机制放在同一条任务链上研究。

从平台设计看，一次批准应当能对应具体对象和条件。工作被委派、等待一段时间，或收到新输入之后，都需要判断原条件是否仍成立。这些条件如果只存在于自然语言历史中，系统就更需要可检查的行为证据。

取消也是同样的问题。用户希望停下的是一项任务、一份职责，还是所有未来触发？这些范围需要明确表达，并且让执行链逐步收敛。停止不能自动抹去已经发生的副作用，我会把补偿和结果核对单独记录。

## 6. 模型与 Harness 应作为实验配置一起看

[系统卡阅读](../models/astra-system-card/)给我的收获，是把长期任务评估放回完整运行条件。确认策略、任务序列、时间预算和上下文都会影响结果；模拟实验与产品真实运行也有不同的证据范围。

后续比较时，我更愿意保留可复核的目标、过程、产物和人工介入，再说明当时的模型与环境。仅引用模型名或一项测试分数，很难回答我的具体职责是否能被可靠承接。

[外部观察](../practice/external-observations/)也提醒我，交互入口与状态反馈本身就是产品可靠性的一部分。不过个别演示或客户端报告不能直接代表全部任务效果，我会继续把它们与自己的实验分开。

## 7. 与 Muse 的初步对照，以及下一步

目前两轮学习使用了同一套主题，但证据并不对称：Muse 已有我的环境与行为探索，Dots 这轮主要是公开资料。现阶段适合比较设计问题，还不适合给运行可靠性排名。

| 我想继续比较的问题 | 下一步需要补的证据 |
| --- | --- |
| 长期职责怎样变成任务 | 多轮输入、任务关联和结果回传 |
| 目标与记忆怎样更新 | 更正前后各任务实际使用的信息 |
| 执行环境怎样恢复 | 离线、回收或超时后的动作与产物 |
| 授权与取消怎样传播 | 原批准对象、派生动作和停止后的记录 |
| 减少了多少用户负担 | 验收质量、耗时、成本及人工接管 |

我已经把这些问题整理成 [待实测方案](../practice/validation-plan/)。接下来会先积累完整任务记录，再回头修正对架构与产品能力的理解。

这轮 Dots 学习带给我的主线，是把长期个人代理看成需要持续维护目标、上下文、执行与权限关系的系统。这个视角可以继续带入后面的产品调研，也能帮助我检查自己的平台设计还缺少哪些语义。
