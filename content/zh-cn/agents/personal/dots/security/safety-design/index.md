## 官方描述的边界

官方介绍了独立云端工作环境、执行代码与关键保护系统的分离、安全登录，以及 Auto-review。主动研究通过代码限制为只读收集，后续行动另受检查。安全登录让凭证避开模型上下文，保护范围不包括另行写在可读消息或文件里的秘密。[官方安全文章](https://openai.com/index/how-we-build-safety-security-and-privacy-into-dots/)

## 我关注的是保护逻辑能否被执行环境修改

Agent 可以写文件、装依赖和运行代码时，权限判定如果也放在同一个可修改范围中，就需要解释它如何保持约束力。这篇文章提供了明确的设计方向：控制关键检查的系统需要处在代理不能任意修改的边界之外。

我不会由此推断具体服务进程、虚拟化技术或网络拓扑；本轮没有取得独立系统证据。对我自己的平台而言，需要进一步明确什么由操作系统或执行器强制限制，什么依赖模型理解与检查器判断。

## 从主动发现到实际行动

我把主动研究理解为一个受限的信息获取阶段，再将采取行动看作另一项决策。这样既可以寻找与用户目标有关的新信息，也能在真正产生副作用之前重新判断范围。

值得继续研究的是，研究笔记进入主代理上下文时怎样保留来源，以及外部内容中的指令如何与用户授权区分。只读工具限制了直接动作，但信息仍可能影响后续决策，输入来源和行动审查需要连起来看。

## 审查结果也是执行反馈

对 Agent 逻辑，我会把审查拒绝视为需要处理的结果：明确缺的是授权、信息还是某项不可执行条件，然后决定澄清、换允许的路径或停止。同一个已被拒绝的动作换一种包装再试，不能算作可靠恢复。

审查系统与沙箱各有职责，不能仅凭一个组件的名称认定边界完整。实际效果还要对照 [系统卡评估](../../models/astra-system-card/)和 [控制语义](../controls-and-cancellation/)理解。

## 2026-10-26 补充：云代理的 TLS 处理仍未公开（第三方观察与用户报告）

10 月 26 日这轮跟踪读到一条与上面“执行检查在代理改不到的边界之外”直接相关的线索，我把它
单独记在这里，因为它涉及的不是模型行为，而是网络出口的设计是否公开。

**已核验的部分（第三方用户报告，我直接读了原文）：** openai/codex Issue #56358（2026-10-23）
的报告者称，在 ChatGPT / Dot 云执行环境中，对 IPv4 字面量 URL 的 HTTPS 请求在 TLS 身份校验
阶段失败，原因是环境 HTTPS 代理返回了一张代理生成的叶证书，签发方为 OpenAI（O=OpenAI, LLC），
而非源站的公开 CA 证书；该叶证书没有可用的 iPAddress SAN。报告者做了离线对照：同一源站在
不经该代理的机器上出示 Let's Encrypt 证书且校验通过，因此不匹配只出现在云代理路径上。
这份报告本身是连通性故障报告，不是数据泄漏的证据。

**转述的部分（社区整理，尚未独立核验）：** ExplainX 2026-10-25 的整理文章据此与一则 Ask HN
帖子（同日）提出，Dots 云代理可能对 HTTPS 做终止并重签发；文章同时明确区分了“技术上可能
被读取”与“是否被记录、保留、用于何种目的”，后者在其审查的来源中没有证据，OpenAI 也未
公开说明该代理的解密范围与日志留存。我直接打开 Ask HN 链接时返回 419，未能独立读到原帖，
所以 HN 一段在这里只记为转述。

**我的理解与待验证问题：** 如果出口代理确实终止 TLS，那么“凭证不进入模型上下文”这一官方
保护与“会话内容经过一个 OpenAI 控制的解密点”是两个不同层次的陈述，前者成立不自动回答后者。
对我自己的平台而言，这提醒我在设计出口代理时就要把“是否解密、解密后记什么、谁能看、
保留多久”写进公开说明，而不是留给用户从证书链反推。待验证：OpenAI 是否会发布相关说明；
该代理是否覆盖全部目的地、全部 Dot 层级与客户端；GitHub 更早的 #53406 与 10 月 8 日报告的
原文细节。ExplainX 文末推广其团队的 AgentBeam 产品，引用其建议时我降级处理，只采信可回溯
到 GitHub 的具体报告。
