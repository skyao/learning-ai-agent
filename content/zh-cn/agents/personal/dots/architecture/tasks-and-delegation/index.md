## 读到的执行行为

文档描述了后台并行 Agent，以及本地 Work/Codex、新云端线程和预先配置的 Codex 云环境。委派任务有自己的对话，只接收该项工作所需的上下文；切换所选电脑不迁移已有任务。周期工作需要保存计划，接入事件源也不自动建立监控。[任务文档](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

## 我关注的是任务归属

我把一项职责拆成三个问题：谁决定下一步，哪个任务承接这一步，它绑定哪个执行环境。对运行平台而言，这比“有几个 Agent 同时工作”更能说明行为。

如果用户在主对话中修改目标，变化需要传播到相关任务，但不能误改同一代理正在处理的其他职责。我想继续核实传播范围、确认方式以及任务已经执行部分动作时的处理。目前没有这部分运行日志。

| 我准备采用的记录维度 | 用途 |
| --- | --- |
| 职责与任务关联 | 判断子任务的结果在推进哪个目标 |
| 目标和约束版本 | 解释中途修改要求后的行为 |
| 原始执行环境 | 查找产物、定位错误和继续任务 |
| 委派输入与结果 | 检查上下文遗漏和结论失真 |

## 持续执行还要考虑时间语义

我想分别观察自主跟进、固定计划和服务事件。三者可能产生相似结果，但触发依据不同：何时算错过、何时重试、何时合并重复事件，都需要各自的定义。

平台还要解决结果回传后的验收。子任务结束时，主代理是否检查产物并更新职责状态，是否仍有未完成依赖？一个执行状态不能单独代表业务目标已满足。

## 委派链路上的授权边界：转述许可不被承认为直接授权（社区报告，2026-10-19 至 10-26）

[外部观察](../../practice/external-observations/)新增小节同一线索，这里记我从中取的机制含义。

官方文档描述的委派模型是：用户给职责，dot 派生任务、跨 Work/Codex 与既有会话推进。
但一则开发者社区一线报告揭示了一个文档未公开的边界：当用户在 dot 对话里授权“你去
告诉 Work 会话做某事”时，这句许可在跨会话投递时可能不被承认为直接来自用户的授权，
调用在投递前被拦截；读取不受影响，发送未到达。报告者两次实例（一次是 Library 与
Project Files 更新、一次仅起草）均被同一理由拦截，重启后重复确认也未通过，帖内暂无
官方给出的受信任确认路径。

我把它理解为“授权的来源”与“授权的内容”在委派链上是分开的两件事：内容上用户确实
说了，但在跨会话投递这一环节，系统只认直接授权、不认经 dot 转述的授权。这一区分若属
实，对运行平台设计有直接启示：跨 agent、跨会话的指令投递需要一条独立的所有者确认
通道，不能默认把对话里的“你去告诉它”当作投递环节的授权凭证。但这仍是单用户样本的
社区报告，不是官方规则说明；是否分动作类型、是否与账号或版本有关、官方是否已有确认
路径，均待核实，我不把它写成 Dots 的普遍行为。

## 同一应用内的读写不对称：dot 能读项目文件，却不能写回（社区报告，2026-10-13 至 10-17）

上一节的委派拦截讲的是“跨会话投递时转述授权不被承认”。这一节是同一主题在另一条
链路上的对照：dot 与 ChatGPT 原生功能之间，读与写并不对称。

开发者社区一则反馈帖记录：用户用 dot 数日，dot 能读其他项目的文件，但请它更新项目
指令时，它只交回一份需要用户自己复制粘贴的文件清单；用户在手机上搬运一次约 12 步，
且常在中途忘记标题。用户问 dot 怎么办时，dot 反问是否可用某个邮箱在自己的云浏览器
里登录 ChatGPT 网页版——即想以用户身份登录来绕过自身没有写入口的限制。跟帖用户提出
了同类诉求：希望在 dot 对话内直接用上 Deep Research、插件选择器等 ChatGPT 内置能力。

我从中取的机制含义是：dot 的“集成”目前更接近“读侧集成”——能看、能引用、能起草，
但写回宿主应用原生对象的入口并不完整。这与上一节的拦截不同：上一节是系统主动拦截
了一次投递，这一节是根本没有写入口、只能退回手动搬运。两者共同说明，评估一个 agent
的集成深度时，读权限与写权限要分开问，不能因为“它能看到我的项目”就默认“它能替我
改项目”。

未见绕过依据，可作旁证，但不是同一证据。截至 2026-10-26 检索，未见官方回应或版本
补齐说明，是否后续版本已改、是否分账号或版本，均待核实，我不把它写成普遍规则。

## 审批在委派链上断裂：Dot 线程里的批准到不了它派生的 Codex 线程（社区长测，2026-10-15）

[外部观察](../../practice/external-observations/)新增小节同一线索，这里记我从中取的机制含义。

前两节分别讲了“跨会话投递被拦截”与“同一应用内有读无写”。这一节是同一主题的第三条
对照，发生在审批的传递环节：metedata 作者 Mete 在一周每日使用中记录，Dot 告诉他，
它启动的另一 Codex 线程需要审批；他在 Dot 对话里说“Approved!”后，Dot 无法把这个
审批转发到那个线程，他必须自己去侧栏对话海里找到该线程手动批准。

我把它理解为委派链上独立的一环——“审批的可传递性”：批准发生在主线程、执行发生在
派生线程，两者之间需要一条系统承认的传递通道；没有这条通道，用户在主线程给出的许可
在执行线程看来等于没给。这与前两节机制都不同：上一节的拦截是系统主动否认了转述授权
的来源资格，这一节的审批来源并无争议、只是传不过去；再上一节的写回缺失是根本没有
写入口，这一节是审批入口存在、但跨线程不连通。评估一个 agent 的委派深度时，读权限、
写权限、投递授权之外，还要单独问一句“主线程的批准能不能到达执行线程”。

证据分层：以上为社区长测作者的一手记录（2026-10-15 发表，自述发布周起每日使用，
全文读取），单作者样本；帖内无官方回应，后续版本是否已修复、是否分账号或版本，均
待核实，我不把它写成 Dots 的普遍行为。

## 审批语义：明确指令本身被当作许可，确认屏没有出现（社区实测，2026-10-07 至 10-09）

[外部观察](../../practice/external-observations/)新增小节同一线索，这里记我从中取的机制含义。

前几节分别讲了“跨会话投递被拦截”“同一应用内有读无写”与“主线程批准传不到派生线程”。这一节是同一主题的第四条对照，发生在审批的语义环节：uehara 作者先把日历连接权限设为“自由读取、改动前确认”，随后明确说“请删除你刚创建的那个事件，不要动其他事件”，结果没有任何确认屏，约 30 秒后事件已删除。作者转述 dot 的事后解释是，它按“请求本身是否明确允许该操作”判断，“只删那个事件”同时明确了目标与操作，故把请求本身当作许可；“起草”则不算发送许可，说“请发送那封草稿”则无确认屏直接发出。

我把它理解为委派链上独立的一环——“审批的语义”：前面几节问的是授权能不能投递、有没有写入口、批准能不能跨线程传递，这一节问的是，在同一个线程里，什么样的表述才算一次批准。如果系统把“说得够清楚”本身当作批准，那么“改动前确认”就不是一道独立于指令的第二道关，而只是对不明确请求的兜底。评估一个 agent 的删改类委派时，读权限、写权限、投递授权、审批传递之外，还要单独问一句“明确指令会不会跳过确认屏”，以及“起草与发送、查看与删除这类动词边界，系统按什么规则切分”。

同一篇实测还给了审批语义的两个配套现象，我一并记在这里，因为它们影响同一条问责链。第一是审批的可见性：删除 Notion 页面时，询问是否可用作者 Mac 上 Chrome 的提示只出现在派生的子对话内，第一次作者未注意到，约 21 分钟后结果记为“aborted by user”，主对话只收到一行“未执行删除”；第二次保持子对话打开并按下“Allow for this conversation”后，1 分 10 秒完成。这与上一节的断裂机制不同：上一节是审批入口存在、但跨线程不连通，这一节是审批入口存在、却只在派生子对话内可见，错过即无声停止。第二是操作的归属：Notion 实际界面把移入回收站的操作记在作者本人名下，因为 dot 用的是作者已登录的 Mac 版 Chrome；对方服务无法区分 dot 的操作与用户本人的操作。批准是否有效、批准出现在哪里、事后审计算在谁名下，是三件要分开核验的事。

证据分层：以上为社区作者的一手实测（2026-10-07 至 10-09 测试，2026-10-10 发表，2026-10-27 页面更新，我读的是 dev.to 原文全文），作者用真实工作账号、逐项对照真实界面核对，单作者样本；作者本人限定只试了一次、“设置可能尚未生效”，帖内无官方回应，后续版本是否已改、是否分账号或版本，均待核实，我不把它写成“设置被绕过”“Auto-review 失效”或 Dots 的普遍行为。

## 跨入口的任务发现不对称：dot 看不到的已有任务，Work 对话却能查到（社区报告，2026-10-07）

前两节分别讲了“跨会话投递被拦截”与“同一应用内有读无写”。这一节是同一主题的第三条对照，发生在任务发现层：开发者社区一则报告称，用户的 dot 无法访问全部已有的 Work 自动化任务，而在一个独立的 ChatGPT Work 对话里，同一批任务可以被完整查询——包括任务指令、排期与启用/暂停状态。

这条线索值得记下的地方在于，它与前两节机制都不同：不是投递被拦截（B7 那类），也不是缺写入口（B9 那类），而是发现层的不对称——dot 连已有任务的完整清单都看不到。跟帖者把问题拆成三个不应混为一谈的问题：任务是否存在、当前入口是否被允许控制它、当前入口是否能通过已暴露的工具发现它。作者本人也明确限定：Work 一侧的查询是已验证的，dot 一侧的缺口是报告观察，未记录缺失子集与工具报错，不主张这是产品级缺陷；三种可能解释（有意的可见性边界、工作区或权限差异、发现/工具可用性缺陷）均未证实。

我从中取的机制含义是：评估 agent 的“协调能力”时，除了读权限、写权限、投递授权之外，还要单独问一句“它能不能发现已有的任务”。一个长期 agent 若看不到用户早已建好的定时任务，就会面临两难：要么放弃协调已有工作，要么重建任务——而重建可能导致两个有效任务并行、产生重复提醒或重复动作。跟帖者提出的安全契约（先发现、再识别归属、再暴露权限状态、最后才允许修改或重建）与“任务存在但我在这个入口无法查看/控制”的明确表态，值得作为跨入口任务连续性的设计参考。

## 审批的范围外溢：同一线程内一次批准，被视为后续发送的许可；邮箱访问权限即登录权限（社区实测，2026-10-13）

[外部观察](../../practice/external-observations/)新增小节同一线索，这里记我从中取的机制含义。

前几节分别讲了“跨会话投递被拦截”“同一应用内有读无写”“主线程批准传不到派生线程”与“同一线程内明确指令本身被当作批准”。这一节是同一主题的第五条对照，发生在批准的范围环节：Zapier 作者 Harry 在同一邮件线程内批准过一次发送后，dot 未经再次询问又发了一封邮件；另因作者给了 dot 邮箱访问权限，dot 用邮件验证码登录多个账号全程未问作者。

我把它理解为委派链上独立的两环。第一环是“批准的范围”：前面几节问的是授权能不能投递、有没有写入口、批准能不能跨线程传递、什么样的表述才算批准，这一节问的是，一次批准到底覆盖单次动作，还是覆盖同一线程的后续动作。如果系统按线程粒度理解批准，用户以为的“批这一次”在系统看来可能是“批这一串”，评估发信类委派时就要单独问一句“批准是按动作计、还是按线程计”，以及“后续发送有没有独立的确认”。第二环是“权限的实际外延”：用户授权的表述是“读邮箱”，系统实际获得的能力却是“以邮箱验证码登录账号”——读权限与登录权限在这里没有分开设关。评估连接权限时，“它能看到什么”和“它能以我的身份登录什么”是两件要分开问的事；邮件验证码这类“邮箱即身份凭证”的登录方式，尤其要单列在授权清单里问。

证据分层：以上为社区作者的一手实测（2026-10-13 发表，自有 Pro 账号接真实 Google 账号使用数日，我读的是 Zapier 原文全文），单作者样本；帖内无官方回应，后续版本是否已改、是否分账号或版本，均待核实，我不把它写成 Dots 的普遍行为。Zapier 本身销售 ChatGPT 集成，文中 9,000+ 应用接入口径为厂商销售口径，不得与 OpenAI 的 4,000+ 插件口径混用；dev.to 10 月 17 日的 mikefluff 整理篇为本篇的二手摘要，我以 Zapier 原文为准。
