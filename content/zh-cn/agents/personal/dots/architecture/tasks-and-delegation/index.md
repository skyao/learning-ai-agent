## 读到的执行行为

文档描述了后台并行 Agent，以及本地 Work/Codex、新云端线程和预先配置的 Codex 云环境。委派任务有自己的对话，只接收该项工作所需的上下文；切换所选电脑不迁移已有任务。周期工作需要保存计划，接入事件源也不自动建立监控。[任务文档](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

## 我关注的是任务归属

我把一项职责拆成三个问题：谁决定下一步，哪个任务承接这一步，它绑定哪个执行环境。对运行平台而言，这比“有几个 Agent 同时工作”更能说明行为。

如果用户在主对话中修改目标，变化需要传播到相关任务，但不能误改同一代理正在处理的其他职责。我想继续核实传播范围、确认方式以及任务已经执行部分动作时的处理。目前没有这部分运行日志。

| 我准备采用的记录维度 | 用途 |
| --- | --- |
| 职责与任务关联 | 判断子任务的结果在推进哪个目标 |
| 目标和约束版本 | 解释中途修改要求后的行为 |
| 原始执行环境 | 查找产物、定位错误和继续任务 |
| 委派输入与结果 | 检查上下文遗漏和结论失真 |
| 等待原因 | 区分等待授权、资源、登录或外部条件 |

这张表是我的分析口径，字段名称不代表 Dots 的内部 schema。

## 持续执行还要考虑时间语义

我想分别观察自主跟进、固定计划和服务事件。三者可能产生相似结果，但触发依据不同：何时算错过、何时重试、何时合并重复事件，都需要各自的定义。

平台还要解决结果回传后的验收。子任务结束时，主代理是否检查产物并更新职责状态，是否仍有未完成依赖？一个执行状态不能单独代表业务目标已满足。

相关问题继续记录在 [运行边界分析](../runtime-boundaries/)和 [待实测方案](../../practice/validation-plan/)。

## 委派链路上的授权边界：转述许可不被承认为直接授权（社区报告，2026-10-19 至 10-26）

[外部观察](../../practice/external-observations/)新增小节同一线索，这里记我从中取的机制含义。

官方文档描述的委派模型是：用户给职责，dot 派生任务、跨 Work/Codex 与既有会话推进。
但一则开发者社区一线报告揭示了一个文档未公开的边界：当用户在 dot 对话里授权“你去
告诉 Work 会话做某事”时，这句许可在跨会话投递时可能不被承认为直接来自用户的授权，
调用在投递前被拦截；读取不受影响，发送未到达。报告者两次实例（一次是 Library 与
Project Files 更新、一次仅起草）均被同一理由拦截，重启后重复确认也未通过，帖内暂无
官方给出的受信任确认路径。

我把它理解为“授权的来源”与“授权的内容”在委派链上是分开的两件事：内容上用户确实
说了，但在跨会话投递这一环节，系统只认直接授权、不认经 dot 转述的授权。这一区分若属
实，对运行平台设计有直接启示：跨 agent、跨会话的指令投递需要一条独立的所有者确认
通道，不能默认把对话里的“你去告诉它”当作投递环节的授权凭证。但这仍是单用户样本的
社区报告，不是官方规则说明；是否分动作类型、是否与账号或版本有关、官方是否已有确认
路径，均待核实，我不把它写成 Dots 的普遍行为。

## 同一应用内的读写不对称：dot 能读项目文件，却不能写回（社区报告，2026-10-13 至 10-17）

上一节的委派拦截讲的是“跨会话投递时转述授权不被承认”。这一节是同一主题在另一条
链路上的对照：dot 与 ChatGPT 原生功能之间，读与写并不对称。

开发者社区一则反馈帖记录：用户用 dot 数日，dot 能读其他项目的文件，但请它更新项目
指令时，它只交回一份需要用户自己复制粘贴的文件清单；用户在手机上搬运一次约 12 步，
且常在中途忘记标题。用户问 dot 怎么办时，dot 反问是否可用某个邮箱在自己的云浏览器
里登录 ChatGPT 网页版——即想以用户身份登录来绕过自身没有写入口的限制。跟帖用户提出
了同类诉求：希望在 dot 对话内直接用上 Deep Research、插件选择器等 ChatGPT 内置能力。

我从中取的机制含义是：dot 的“集成”目前更接近“读侧集成”——能看、能引用、能起草，
但写回宿主应用原生对象的入口并不完整。这与上一节的拦截不同：上一节是系统主动拦截
了一次投递，这一节是根本没有写入口、只能退回手动搬运。两者共同说明，评估一个 agent
的集成深度时，读权限与写权限要分开问，不能因为“它能看到我的项目”就默认“它能替我
改项目”。
