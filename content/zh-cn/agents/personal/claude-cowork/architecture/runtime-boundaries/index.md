## 先分清三件事

我把规划循环、代码执行和资源访问分别画进自己的运行模型，避免把“在桌面端使用”直接理解为“全部在本机完成”。

| 路径 | 官方说明 | 我需要验证的边界 |
| --- | --- | --- |
| 新云端任务 | 会话在服务端隔离环境运行 | 任务状态何时暂停、恢复和过期 |
| 访问本地文件 | 经已连接的 Desktop 和授权文件夹访问 | 断线、撤权和读取后副本的生命周期 |
| 旧版本地任务 | 代理循环在宿主，代码在 Linux VM | 宿主工具、VM 与模型服务的边界不同 |

2026-10-06 起新 Pro / Max 任务默认云端，不能再设置新任务只在本机执行。已有本地任务继续保留。架构说明中的 Mac Virtualization.framework 与 Windows Hyper-V 属于本地执行路径，不能拿来描述所有新云端会话。

## 本地文件仍可能进入云端处理

多端文档强调，文件夹原件留在设备上，任务需要时读取的文件内容会送到服务端处理。桌面桥接也需要应用在线和授权有效。因此“没有整目录预先上传”“能访问本地文件”“内容不出设备”是三个不同命题。

官方架构还将连接器凭证留在服务端代理路径，不交给代码沙箱。我将其理解为缩小代码环境直接持有的秘密范围；它不能替代每次工具调用的权限检查。

## 对运行平台的启发

我更愿意把资源访问看成可独立撤销的能力：云端任务可以存在，本地设备可以暂时不可用，连接器授权也可以中途失效。任务状态应该能表达“仍在运行但等待某个资源”，而不是只有运行与失败两种结果。

本地代理循环也不等于本地模型推理。这份文档没有给出完全离线推理承诺，我不会将本地 VM 写成模型或全部数据都留在本机。
