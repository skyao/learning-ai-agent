## 我对这条路线的理解

这一轮我把 Cowork 从“会操作文件的桌面助手”，重新理解为 Claude 的任务执行路径。统一聊天与执行入口以后，用户可以直接描述结果，系统负责组织多步工作。这对个人知识工作很有吸引力，但也把运行位置、上下文与权限的复杂性留给了平台。

本轮基于截至 **2026-10-21** 的中英文公开资料，没有账号实测。下面的结论是阅读后的阶段性理解，具体行为与待验证项保留在各主题笔记中。

## 10 月 23 日补充：与 Duet 一起理解个人委托

我新增了 [Claude Duet 调研](../../claude-duet/)，将它与 Cowork 分别保留。Duet 补充主动检查、判断何时打扰用户和持续跟进的样本；Cowork 原有的文档交付、后台任务与周期执行仍是重要研究对象。

共享账号记忆和配置让我更关注跨入口纠错与访问范围，而不是简单增加一项“有记忆”能力。下一步会用同一材料包比较用户发起交付与主动发现变化，再记录任务验收、人工介入和后台用量。新增资料读取于 2026-10-23，原有 Cowork 资料继续保留 10 月 21 日的证据范围。

## 变化首先发生在运行环境

2026-10-06 起新 Pro / Max 任务转为云端，旧本地任务继续保留。我不能再把所有 Cowork 描述为本地 Linux VM，也不能从“云端运行”推成任意本地资源都能脱机访问。

[运行边界笔记](../architecture/runtime-boundaries/)分别整理代理循环、代码环境和桌面资源桥接。对我开发运行平台的工作，最有价值的是这几层可以独立存在：会话仍在云端，桌面可能断线，某个连接器也可能刚被撤权。任务状态需要表达这些中间情况。

## 个人上下文是有范围的状态

[Projects 与记忆](../architecture/projects-and-memory/)让我重新审视“项目隔离”。项目默认可以使用账号记忆，真正的上下文范围要看设置；记忆、聊天检索和本地材料也各有自己的控制。

我更关心事实如何更新、错误如何纠正、项目约束如何避免跨域传播。这些问题比是否有一个 Memory 入口更接近长期助手能否被信任。把所有偏好与事实混成统一用户画像，会使后续纠错变得困难。

## 持续执行不等于长期负责

[周期任务](../architecture/scheduled-tasks/)能承载重复工作，但我仍需要验证任务是否处理变化、保留进度并在目标完成后停止。纯云端任务的离线运行与依赖本地应用的任务不能共用一条结论。

定时任务帮助仍有本地资源任务运行位置的措辞差异，我保留待核实。对平台而言，计划与每次运行应有独立身份，暂停触发、取消当前执行和删除历史分别给出明确语义。

## 工具通道决定真实能力边界

[Skills 与 Plugins](../integrations/skills-and-plugins/)支持方法和配置复用，但不能替代工具授权。[浏览器与电脑操作](../integrations/browsers-and-computer/)则说明，相同目标可以走连接器、内建浏览器、Chrome 或屏幕操作，在线条件与隔离范围并不相同。

我的理解是，平台应把执行通道保留为可观测事实。用户同意更新一条数据，并不自动等于允许系统换一种方式绕过原来的限制。代码网络策略也不能代替对其他工具出口的控制，详见 [审批与网络权限](../security/permissions-and-network/)。

## 我想带回自己工作的几个设计问题

| 问题 | 我目前的认识 |
| --- | --- |
| 如何呈现统一入口 | 在动作和副作用出现时解释环境与权限 |
| 如何维护个人上下文 | 保留来源、范围、更新与纠错路径 |
| 如何支撑长期委托 | 分开管理目标、计划与单次运行 |
| 如何解释失败 | 关联输入、工具、审批、资源与产物 |
| 如何结束一项委托 | 分别处理执行、计划、记忆、文件与授权 |

[OTel 阅读](../security/observability/)给出了可观测性的具体参考；[生命周期笔记](../security/data-lifecycle/)提醒我，删除对话未必能结束所有派生状态。组织版 Beta 的规则仍需保持适用范围。
