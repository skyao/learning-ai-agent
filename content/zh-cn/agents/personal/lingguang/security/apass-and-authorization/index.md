## 两份一手资料分别说明什么

[灵光 2.0 公告](https://www.antgroup.com/en/news-media/press-releases/1793066400000)确认接入 APASS，并描述授权密钥与 Agent 分离托管、用户可以查看和撤销授权。这是产品层面的官方声明，本轮没有安全测试。

[支付宝 APASS 官方页](https://aipay.alipay.com/act/apass)进一步区分可信身份、持续核身、意图安全和可信存证。页面把 Agent 静态身份、运行时身份与责任主体分开，并将身份、授权、核验与交易处置结果纳入追溯范围。读取于 **2026-11-02**；页面页脚显示更新于当日，不能把这个页面更新时间当作 APASS 首次推出日期。

APASS 面向更广的商家、支付机构与 Agent 生态。**平台提供某项能力，不表示灵光已在每个工具上启用同一套控制。**

## 我从平台开发角度得到的理解

我认为这里至少有三层信息需要保持独立：谁委托、哪个运行实例执行、这次动作具体被允许做什么。只保存用户账号和一枚长期令牌，不足以解释一个持续运行的代理为什么能够在此刻发起某项动作。

类似地，服务账号的授权可以长期存在，但某一次购买、对外发送或设备控制，仍可能需要更窄的批准。授权凭证、意图证明和付款批准不应被写成同一种凭证；公开页面也不足以确定它们在灵光内部的实际结构。

## 我仍需验证的边界

1. 用户撤权时，正在执行的任务能否及时停止后续访问？已经提交的外部动作怎样反馈？
2. 用户批准的对象、金额或接收人变化后，旧批准是否失效？
3. 用户能否查看可理解的执行记录，而不仅是后台存在审计日志？
4. 删除记忆、断开连接器和删除云端工作文件是否分别有入口及保留规则？

上述是我的验证问题，没有完成实验。任务与结果的区分见[运行机制笔记](../../architecture/memory-and-task-lifecycle/)。
