## 我读到的动作边界

官方列有邮件、日历和文件等应用动作。共享 Docs / Sheets / Slides 的修改需审核并确认计划；私有 Google Tasks 的批量动作则可无需再次确认。[官方动作说明](https://support.google.com/gemini/answer/17094507?hl=en)

这里的 Google Tasks 是待办应用，Task 模式是代理任务入口，两者不能按名称合并。连接 Workspace 应用与使用企业 Workspace 账号，也属于不同问题。

## 我按业务对象理解整合

在学习笔记场景中，一次委托可能读取发布邮件、定位原有资料、更新文档，再创建一项后续待办。我想关注的是对象之间的关系：更新的是哪份文件，待办指向哪项未完成工作，邮件是否真的需要发送。

我会为自己的平台考虑以下动作记录：

| 记录内容 | 对应的问题 |
| --- | --- |
| 对象标识与原版本 | 是否改错文件、依据过时状态写入 |
| 读取来源和事实时间 | 新结论从哪里来，是否仍有效 |
| 计划修改与实际差异 | 批准内容和最后写入是否一致 |
| 业务回执与后续核对 | 工具报告成功后，应用内是否真的生效 |
| 补偿或人工修复入口 | 错误更新后怎样定位并恢复 |

这些是我的设计分析，公开动作列表没有证明 Spark 已完整暴露这些记录。

## 确认策略要细到动作与对象

共享文件与私有待办的规则不同，说明不能把所有应用动作归纳成“写入前必问”或“连接后随意写”。我需要把对象归属、动作类型和用户原始委托放在一起观察。

对平台开发，我更想验证审批期间发生变化的情况：我确认了一份计划，但协作者随后改了原文件，代理会重新检查差异、覆盖修改，还是再次询问？这个实验能帮助我理解批准的究竟是抽象目标，还是针对特定版本的具体修改。

近期外部用户曾报告写入故障并随后回报恢复，见 [外部观察](../../practice/external-observations/)。它提供了复现与排障问题，尚不能替代我自己的权限实验。
