## 我从文档中提取的边界

Personal Intelligence 通过连接的应用关联个人信息，应用可单独连接或断开。对于从应用获知的信息，官方要求同时删除含有该信息的聊天、断开来源应用，才能避免从另一条路径继续使用；源数据更新或删除后，Gemini 体验可能过几天才受影响。[官方个性化说明](https://support.google.com/gemini/answer/16598406?hl=en)

过去聊天的 Memory 另有开关与适用范围，例如 Gems、Live 存在专门限制。[官方 Memory 帮助](https://support.google.com/gemini/answer/16598469?hl=en)

## 我把“了解我”拆成来源关系

我希望把以下几类信息分别观察：

| 信息 | 我的学习场景 | 需要检查什么 |
| --- | --- | --- |
| 原始业务数据 | 收藏的发布邮件、日程与文档 | 是否仍有效、修改时间与访问范围 |
| 过去聊天 | 我曾经讨论过的产品判断 | 当时假设是否被当成确定事实 |
| 长期指令 | 第一人称、学习笔记、保留证据限制 | 是否在新的任务中继续生效 |
| 当前任务上下文 | 这轮只研究 Spark，不扩充清单 | 是否覆盖一般偏好、何时失效 |
| 执行中的材料副本 | 已读取的文章与生成中的提纲 | 来源变更后能否更新 |

这是我的信息来源模型，不能据此认定 Google 使用了某种向量库、画像数据库或统一记忆文件。

## 更新延迟会影响行动

“几天后才影响体验”对普通回答和实际动作的含义不同。如果我更改了项目评审的时间，代理仍用旧日程生成材料，可能只是多做了一次工作；如果它依据旧地址把产物发送出去，后果就涉及外部状态。

对自己的平台，我会区分“可以沿用的背景知识”和“执行前必须重新核验的业务事实”。后者应该有来源、时间和有效条件。这里是我的设计判断，当前资料没有说明 Spark 对每一项事实怎样做最终校验。

## 遗忘是多个副本共同变化

断开连接能够阻断一条后续访问路径，却不能自动解释先前读入的内容和已生成产物。反过来，删除聊天后，只要原始来源仍可访问，事实仍有可能再次进入上下文。

我准备以一项人工设定的偏好观察：首次读取、来源更正、聊天纠正、断开应用与删除聊天分别产生什么效果，并给每次观察标注时间。具体方法见 [实践计划](../../practice/validation-plan/)。涉及远程浏览器和代码文件的数据清理，另见 [生命周期笔记](../../security/controls-and-data-lifecycle/)。
